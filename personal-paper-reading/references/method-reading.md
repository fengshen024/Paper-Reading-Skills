# 机制与公式讲解

## 从模块名到实际操作

先用一段话重建端到端流程，然后只展开理解贡献所需的细节。每个关键模块回答：

| 问题 | 解释应包含的内容 |
|---|---|
| 为何需要 | 它处理前一阶段哪个具体限制；作者理由与解释性推断分开 |
| 输入是什么 | 数据对象、表示来源、必要形状；缺失维度不猜填 |
| 如何计算 | 实际聚合、采样、检索、打分、更新或约束，避免只重述模块名字 |
| 输出去哪里 | 中间结果如何连接下一模块，是否进入损失或直接用于推理 |
| 何时变化 | 是否依赖当前查询／支持集，训练与推理是否重新计算 |
| 如何学习 | 可训练参数、冻结模块、参数共享、梯度路径和损失 |
| 带来什么代价 | 计算、内存、额外数据或适用假设；没有测量时不能定量断言 |
| 什么证据支持 | 消融、替代设计、理论条件，或仍只有作者解释 |

对于“全局表示”“相似关系”“自适应”“去噪”等词，要解释其计算范围和依据。例如，全局向量可能是固定平均、按关系缓存、按支持集重算或查询条件化，不能把这些情形混称为动态检索。

## 公式的讲解顺序

1. 先说明公式回答什么问题，再给核对过的原式与编号。
2. 定义关键符号及运算范围，交代输入的来源和输出的用途。
3. 指出决定行为的部分：分母、掩码、温度、求和轴、归一化、采样和停止梯度。
4. 用直觉或小例子解释该操作；数值为自造时标为教学示例。
5. 说明公式如何连接训练目标和推理决策。仅在理解或复现需要时展开推导。

不要求抄写每条公式。对关键目标不能省略改变其含义的正负号、期望分布、分母或约束；无法从截图辨认时说明哪些项未确认。

遇到信息论界、概率建模、半环或其他理论结果时，核查随机变量、适用条件和结论之间的关系。有限数值例子可以发现反例或实现错误，不能证明一般定理。某个训练目标与理论表达式形式相似，也不代表已经满足其假设。

## 训练与推理要分开

至少交代：

- 训练数据如何构造，正负样本和监督／自监督信号来自哪里。
- 各模块联合、交替还是分阶段优化，哪些参数共享或冻结。
- 推理新增了什么输入，是否更新参数，是否重建支持表示，如何生成或排名候选。

论文没有说明的训练关系标为缺失细节，不能因为两种做法都能设想就回答“都可以”。

## 图、例子与代码

优先解释原架构图的实际箭头；自绘图标为解释性重绘。训练反馈箭头、推理数据流与评估环节应能区分，不能凭布局补出不存在的依赖。

只有模块或公式解释仍抽象时才补一个贯穿的小例子。例子应足够简单，且不冒充原文案例或实测结果。

用户问“代码中如何体现”时，定位实际代码中的调用关系、张量来源及更新位置，并引用核实的文件和行号。记录仓库版本或 commit（可取得时）；论文和实现冲突则分别报告，不能静默以一方替换另一方。

没有代码时可提供 `解释性伪代码，未核对作者实现`。阅读代码与运行训练是不同任务，不要为了补充笔记自动开始完整实验。
